# Data Quality Notes — Phase 1 Findings

This document logs the data quality issues identified during the initial EDA phase, outlining how they will be handled in Phase 2 (Feature Engineering).

### 1. `members_v3.csv`
- **Gender Missingness:** A significant portion of users do not report their gender. 
  - *Phase 2 Action:* Impute with "Unknown" or treat missing as a distinct categorical level, rather than attempting statistical imputation, as "refusal to answer" can be an informative signal in churn.
- **Age (`bd`) Outliers:** There are implausible ages present (e.g., negative values, values > 100).
  - *Phase 2 Action:* Clip or nullify values outside a reasonable range (e.g., 0-100) or bin them into an "Unknown/Invalid" category alongside true nulls.
- **Registration Methods:** Certain registration methods (`registered_via`) may be sparse or discontinued. 
  - *Phase 2 Action:* Roll up very low-frequency categories into an "Other" bucket.

### 2. `transactions_v2.csv`
- **Duplicate Daily Transactions:** Users sometimes have multiple transaction records on the exact same `transaction_date` (often due to same-day plan changes, cancellations, or data glitches).
  - *Phase 2 Action:* Sort by date and sequence (or list price) and take the *last* valid transaction for a given day, or aggregate daily transaction features intelligently (e.g., total spent that day) rather than just dropping blindly.
- **Right-Censoring:** The number of transactions naturally tapers off at the very end of the time window because users whose memberships expire much later haven't generated new renewal transactions yet.
  - *Phase 2 Action:* Ensure feature engineering windows respect the "history cutoff" strictly to avoid data leakage from the future.

### 3. `user_logs.csv`
- **Synthetic Data Limitations:** The current file in `data/raw/user_logs.csv` is synthetic and covers only ~8,000 users. 
  - *Phase 2 Action:* The feature engineering pipeline (`src/features.py`) **must** be written to be size-agnostic (using DuckDB chunking) so it won't crash when the real 30GB+ file is swapped in.
  - *Re-validation:* The current patterns (e.g., intentional 41% drop in listening time for churners) are hardcoded by the synthetic generator. These exact percentages are *not* KKBox reality and must be re-analyzed once the real data is loaded.
- **Nulls in Logs:** Minimal nulls expected, but 0-second listening days might exist or be implicitly missing (no row for that day).
  - *Phase 2 Action:* Treat missing days as 0 listening time when aggregating over a window (e.g., 14-day or 30-day lookback).

*Note: The exact null percentages and class imbalance ratios can be interactively generated by running `notebooks/01_eda.ipynb`.*
